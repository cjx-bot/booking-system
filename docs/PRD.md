# PRD · 预约系统 MVP

> 版本：v1.0（契约冻结基线）
> 对应任务：T0.1
> 下游消费者：Agent-Infra、Agent-Data、Agent-Auth、Agent-Marketing、Agent-Algo、Agent-Booking、Agent-Dashboard、Agent-Notify

---

## 1. 一句话定位

给独立职业者一个可分享的预约链接，访客自助选时段，主人只管赴约。

（28 字）

---

## 2. 目标用户

**独立职业者**：教练、顾问、设计师、咨询师、私教、牙医、摄影师。

判定标准（三条同时满足才算目标用户）：

| 维度 | 目标用户 | 非目标用户 |
|---|---|---|
| 人数 | 1 人提供服务 | 2 人以上需要排班分配 |
| 排期 | 固定周循环（周一至周五 9-18） | 复杂轮班、跨时区团队 |
| 客户来源 | 自己发链接（私信 / 名片 / 主页） | 平台派单、需要表单路由分流 |

**明确不是企业团队。** 任何"多成员 / 组织 / 角色权限"的需求都进非目标清单。

---

## 3. 本期功能（8 条）

### F1 单人预约链接

**用户故事**：作为主理人，我把 `mysite.com/demo/30min` 发到微信，客户点开就能看到可预约时间。

**验收标准**
- 未登录访客可直接访问 `/[username]/[slug]`，不跳登录页
- `username` 不存在 → 404；`slug` 不存在或 `isActive=false` → 404
- 页面标题包含事件类型名称与主理人名称
- 移动端 375px 宽度下无横向滚动

**涉及数据表**：`User`（查 username）、`EventType`（查 slug + isActive）

---

### F2 事件类型管理

**用户故事**：作为主理人，我能建多个可预约项目（30 分钟初谈、60 分钟深度咨询），分别设置时长和描述。

**验收标准**
- 可创建、编辑、删除、启用/停用事件类型
- 字段：标题（必填 1-60 字）、slug（必填，小写字母数字连字符）、描述（选填 ≤500 字）、时长（15/30/45/60/90 分钟档位）、buffer 前后各 0-60 分钟
- 同一用户下 slug 不可重复，重复时返回字段级错误而非 500
- 停用后公开页 404，但已有预约不受影响

**涉及数据表**：`EventType`

---

### F3 周可用时间

**用户故事**：作为主理人，我设置"周一至周五 09:00-12:00、14:00-18:00"，系统按此生成可预约时段。

**验收标准**
- 按星期（0=周日 … 6=周六）设置，每天可设多段
- 时间段用「从 00:00 起的分钟数」存储，09:00 = 540，18:00 = 1080
- 同一星期内时间段不得重叠，重叠时拒绝保存并提示具体冲突段
- 保存为全量覆盖（先删后插，同一事务内），不是增量

**涉及数据表**：`Availability`

---

### F4 时段生成

**用户故事**：访客打开预约页，系统立刻给出未来 14 天里真正能约的时间点。

**验收标准**
- 输入：事件类型（时长 + buffer）、可用时间、已有预约、访客时区、当前时间
- 输出：按访客时区分组、按天分组的 `Slot[]`，每项含 UTC 起止时间
- 必须满足：不被已有预约占用（含 buffer 前后扩张）、不早于当前时间 + 最小提前量（默认 60 分钟）、不超出可用时间窗
- 夏令时切换日不产生重复时段、不丢失时段
- 纯函数，无数据库调用，可单测；同一输入永远同一输出

**涉及数据表**：无（纯函数，输入由 F1/F3/F5 的数据组装后传入）

---

### F5 预约提交

**用户故事**：访客选好时段，填姓名和邮箱，点确认就占住了这个时间。

**验收标准**
- 必填：姓名（1-50 字）、邮箱（合法格式）、startTime（ISO 8601 UTC）
- 时区由浏览器 `Intl.DateTimeFormat().resolvedOptions().timeZone` 自动带上，用户可改
- 并发同一时段两次提交，只有一次成功，另一次返回"该时段已被预约"（依赖数据库唯一约束，不靠应用层判断）
- 提交成功后跳转 `/booking/[id]`
- 邮箱格式非法时返回字段级错误，不清空已填内容

**涉及数据表**：`Booking`（唯一约束 `(eventTypeId, startTime)`）

---

### F6 确认页与邮件

**用户故事**：预约成功后，我看到明确的日期时间（含时区）和取消方式；同时收到一封确认邮件。

**验收标准**
- 确认页展示：事件名称、主理人、日期、时间段（访客时区 + 主理人时区并列）、访客姓名邮箱、预约编号
- 确认页可被访客凭链接再次打开（不可枚举，ID 为 cuid）
- 邮件在预约成功后 10 秒内发出；发送失败不回滚预约，但记录日志
- 邮件正文含 `.ics` 附件，可一键加入日历
- 邮件同时发给访客和主理人

**涉及数据表**：`Booking`

---

### F7 管理后台

**用户故事**：作为主理人，我登录后能看到所有预约，改事件类型，改可用时间。

**验收标准**
- 未登录访问 `/dashboard/*` 任意路由 → 重定向 `/login?callbackUrl=原路径`
- 后台五个页面：概览、事件类型、可用时间、预约列表
- 预约列表支持按状态筛选（全部/已确认/已取消）、按时间倒序、分页（每页 20）
- 只能看到和操作自己的数据，越权访问他人资源返回 404（不是 403，避免泄露资源存在性）
- 取消预约需二次确认

**涉及数据表**：`User`、`EventType`、`Availability`、`Booking`

---

### F8 时区处理

**用户故事**：客户在纽约打开我的链接，看到的是纽约时间；我后台看到的是上海时间，双方不会约错。

**验收标准**
- 数据库所有时间字段统一存 UTC（`timestamptz`）
- 时区只存 IANA 名（`Asia/Shanghai`、`America/New_York`），绝不存 `+08:00` 这类偏移量
- 主理人时区来自 `User.timezone`，访客时区来自预约表单
- 确认页与邮件同时展示两个时区
- 夏令时由 `Intl` / `Temporal` 计算，不手写偏移表

**涉及数据表**：`User.timezone`、`Booking.guestTimezone`

## 4. 明确不做（10 条）

| # | 不做的功能 | 为什么不做 | 以后要加会动到哪些表 |
|---|---|---|---|
| N1 | 团队排班 / Round-robin | 目标用户是独立职业者，1 人场景下这套逻辑全是空转 | 新增 `Team`、`TeamMember`、`EventTypeAssignment`；`EventType.userId` 改为可空并加 `teamId`；`Booking.hostId` 语义变为"实际承接人" |
| N2 | Routing Forms 表单路由 | 需要先有"多事件类型 + 条件分支"，当前 8 条功能里没有分流需求 | 新增 `RoutingForm`、`RoutingFormResponse`、`RoutingRule`；`Booking` 加 `routingResponseId` |
| N3 | Workflows 自动提醒 | 提醒的前提是"预约会爽约"，MVP 阶段先把确认邮件跑通 | 新增 `Workflow`、`WorkflowStep`、`WorkflowRun`；`Booking` 加 `reminderSentAt` |
| N4 | 支付（Stripe） | 收钱要先有退款策略、对账、发票，任何一个没想清楚都比不做更糟 | `EventType` 加 `priceCents`、`currency`；新增 `Payment`、`Refund`；`Booking` 加 `paymentStatus`、`paymentIntentId` |
| N5 | 日历双向同步 | OAuth 授权 + 增量同步 + webhook 续订，工作量超过整个 MVP | 新增 `CalendarConnection`、`ExternalEvent`；`Booking` 加 `externalEventId`；F4 时段生成要额外排除外部事件 |
| N6 | 视频会议集成 | 没有真实客户前，给每条预约挂 Zoom 链接是伪需求 | `EventType` 加 `locationType`、`locationValue`；`Booking` 加 `meetingUrl` |
| N7 | Embeds 与 API v2 | 对外 API 要先有稳定的内部契约和版本策略 | 新增 `ApiKey`；`Booking` 加 `source`、`externalId`；需要独立的 `/api/v2/*` 路由层 |
| N8 | 多语言 i18n | 目标用户与访客都在中文环境，翻译成本换不来转化 | 所有含文案的表加 `_en` 后缀列或新增 `Translation` 表；路由加 `[locale]` 前缀 |
| N9 | 组织 / 权限体系 | 单人系统里"权限"只有一个值：全有 | 新增 `Organization`、`Membership`、`Role`；几乎所有表的查询都要加 `organizationId` 过滤 |
| N10 | App Store 与第三方集成 | 生态的前提是有开发者，有开发者的前提是有用户 | 新增 `App`、`AppInstallation`、`OAuthClient`；需要对外 webhook 投递队列 |

**范围纪律**：以上 10 条中任意一条在中途被加入，对应的表结构变更会同时阻塞 Wave 3 的三条并行线。要加就等 v2，不要在 MVP 里"顺手"。

## 5. 关键约束（跨功能）

1. **时间只有两种形态**：数据库里是 UTC `DateTime`，展示时是某 IANA 时区的本地时间。代码里不出现第三种。
2. **防重复靠数据库**，不靠先查后写。`@@unique([eventTypeId, startTime])` 是唯一权威。
3. **越权返回 404**，不返回 403。
4. **写操作全部走 Server Action**，入参必须先过 Zod `safeParse`，返回 `{ ok, data } | { ok, error, fieldErrors }`，不抛异常给客户端。
5. **`lib/` 不许 import 任何组件**，`components/ui/` 不许 import 业务代码。

## 6. 成功标准

| 指标 | 目标 |
|---|---|
| 从打开预约页到提交成功 | ≤ 4 次点击 |
| 时段生成函数单测覆盖 | 分支覆盖 ≥ 90%，含夏令时用例 |
| 预约并发冲突 | 0 例双写（由 DB 唯一约束保证） |
| Lighthouse 性能（首页） | ≥ 90 |
| 首屏 JS（预约页） | ≤ 180 KB gzip |

二 · 总体判断 先回答问题：「这是屎山吗」

不是屎山。这是一份中上水平的代码，问题不在「乱」，在「契约有洞」。

按通常判屎山的七个指标逐条对：重复冗余、超长函数、深层嵌套、命名混乱、硬编码、缺注释、高耦合。其中只有第 5 项（硬编码）比较严重，其余都在可接受范围，有些甚至比多数商业项目做得好。

做对的地方

· 全库 0 个 any、0 个 ts-ignore（只有 1 处 eslint-disable）
· app → components → lib 单向依赖，边界清楚
· 注释写的是「为什么」不是「是什么」，可读性高
· 最危险的时段算法抽成纯函数，40 个单测覆盖夏令时/跨时区
· 设计令牌集中在 globals.css，无 tailwind.config 散落
· 生成代码隔离在 lib/generated，一眼能分清

真正的系统性问题

· 抽象建了却不用：requireSession、groupSlotsByDate、formatDateInTimeZone、4 个查询函数全是死代码
· 用了却没抽象：时区格式化在 5 处各写一遍、鉴权样板在 5 个页面各写一遍、isUniqueViolation 复制两份
· 这一对加起来，就是「伪复用」——比堆垃圾代码更隐蔽，因为读起来每处都干净，全局看是在重复劳动

#1同一主理人、同一时刻，可以被约两次（跨事件类型）

位置 prisma/schema.prisma:140 · lib/actions/booking.ts:67-107

现象防重复预约的唯一权威是 @@unique([eventTypeId, startTime])。这个约束只保证「同一个事件类型在同一时刻只有一条」，不保证「同一个人在同一时刻只有一条」。而应用层的 isSlotBookable() 是「先查占用、再插入」——两个请求只要在查与插之间错开，就都能通过。

实测已复现直接对 dev.db 插入两条：30min 与 60min，都放在 2026-11-15T08:00:00Z。

插入成功：30min @ 2026-11-15T08:00:00.000Z
插入成功：60min @ 2026-11-15T08:00:00.000Z
同一时刻共存的预约数: 2  ← 双预约成立

影响真实场景：两个客户同时打开你的公开页，一个约「30 分钟初谈」、一个约「60 分钟深度咨询」，都选了周三 16:00。两人都收到确认邮件，你到点只能见一个。README 里「防重复只靠数据库唯一约束」这句话，在跨类型场景下不成立——这是项目最核心的设计承诺出现了缺口。

建议让唯一性绑在「人 + 时间」而不是「项目 + 时间」。SQLite 不支持部分索引，最省事的做法是加一张占位表，与预约在同一事务里写：

// schema.prisma 新增
model BookingLock {
  id       String @id @default(cuid())
  hostId   String
  startAt  DateTime
  @@unique([hostId, startAt])   // 真正的并发闸门
}

// createBooking：把 create 和 lock 放进同一事务
await prisma.$transaction([
  prisma.bookingLock.create({ data: { hostId, startAt: startAt } }),
  prisma.booking.create({ data: { ... } }),
])

迁移到 PostgreSQL 后可直接用排他约束，一个 DDL 解决，不用改业务代码：EXCLUDE USING gist (hostId WITH =, tstzrange(startTime, endTime) WITH &&)。

#2取消预约没有任何归属校验，任何登录用户可取消别人的预约

位置 lib/actions/booking.ts:150-190 · 调用方 app/dashboard/bookings/page.tsx:21-34

现象cancelBooking 只做了 findUnique({ where: { id } })，既没取 session，也没比对 booking.hostId。而它被注册成了 Server Action——本质是一个公开可 POST 的端点。同时 /booking/[id] 页面把编号直接展示在页面上（第 122-126 行），邮件里也带这个链接。

影响拿到任意一个 booking id 的人，只要有个账号，就能取消那条预约。cuid 不可枚举，所以不是「拖库」级风险，但破坏性操作零授权这件事本身不该存在。另外注意：注释写着「访客凭预约 ID 也能取消」，可访客端根本没有取消入口——这个能力既没实现，又留下了洞。

建议分两条路走清楚，别混着：

// 主理人取消：必须验宿主
const userId = await requireUserId()
if (!userId) return fail('请先登录')
const booking = await prisma.booking.findFirst({
  where: { id: parsed.data.id, hostId: userId },   // 关键：where 里带 hostId
  select: { id: true, status: true, startTime: true },
})

// 访客取消：另开一个 action，用签名 token 而不是裸 id
// token = HMAC(bookingId + 过期时间, AUTH_SECRET)，邮件链接带它

顺带说：现在取消是点一下直接生效、无二次确认、不可撤销（第 143-152 行）。误触就是一条真实预约被取消，建议加确认。

#3访客时区在服务端和客户端算出来不一样，必然触发水合报错

位置 components/booking/BookingFlow.tsx:105-110（另见 64-97 的分组逻辑）

现象

const [guestTimezone] = useState<string>(() => {
  if (typeof Intl === 'undefined') return hostTimezone
  return Intl.DateTimeFormat().resolvedOptions().timeZone || hostTimezone
})

注释说「服务端渲染时先用主理人时区占位，挂载后立刻用真实时区覆盖」。但 useState 的初始化函数不是 useEffect：它在 SSR 时跑一次（拿到服务器的 Asia/Shanghai），在客户端 hydration 时又跑一次（拿到浏览器的时区）。两次结果不同，React 就会判定水合失败。已确认 SSR 输出里访客时区恒为服务器时区：

$ curl .../demo/30min | grep -oE "Asia/Shanghai" | wc -l
5   ← 不管访客在哪，服务端都按 Asia/Shanghai 渲染

影响海外访客每次打开预约页，控制台一条 hydration 报错，日期分组和时段会被整块重算重绘。这也是为什么这个组件没法享受 SSR——它渲染出来的东西对一半用户是错的。

建议时区必须延迟到挂载后设置：

const [guestTimezone, setGuestTimezone] = useState(hostTimezone)
useEffect(() => {
  const tz = Intl.DateTimeFormat().resolvedOptions().timeZone
  if (tz) setGuestTimezone(tz)
}, [hostTimezone])

首屏显示主理人时区、挂载后切到访客时区，这次才是真的「不会闪」。

#4邮件发送失败会被当成成功，日志里永远看不到「发送失败」

位置 lib/email/send.ts:68-91

现象

const results = await Promise.allSettled([ resend.emails.send(...), resend.emails.send(...) ])
const failures = results.filter((item) => item.status === 'rejected')
if (failures.length > 0) { ... return { sent: false, reason: 'partial-failure' } }
return { sent: true }

查了 resend@6.37.0 的类型定义：send() 返回 Promise<CreateEmailResponse>，也就是 { data, error } 的联合体——API 报错时不 throw，而是把 error 放在返回值里。只有网络层异常才会 reject。

影响域名没验证、收件人被退信、配额超限——这些最常见的失败全部走 fulfilled 分支，failures 永远是空数组，函数返回 { sent: true }。运营上会变成「以为发了，其实一封没到」，而这条链路上没有任何一处会告诉你。

建议

const results = await Promise.allSettled([...])
const failed = results.filter((r) =>
  r.status === 'rejected' || (r.status === 'fulfilled' && r.value.error)
)
if (failed.length > 0) {
  console.error('[email] 发送失败', failed.map((r) =>
    r.status === 'rejected' ? r.reason : r.value.error))
  return { sent: false, reason: 'partial-failure' }
}

#5编辑弹窗会显示上一个项目的内容（defaultValue 在常挂载的 Dialog 里失效）

位置 components/dashboard/EventTypeManager.tsx:190-303 · 根因 components/ui/Dialog.tsx:101

现象Dialog 只切换原生 <dialog> 的 open 状态，子元素始终挂载在 DOM 里。表单用的是 defaultValue={editing?.title ?? ''}（第 198、216、241、255、272、289、300 行）——非受控输入框一旦被用户改过，就进入 dirty 状态，之后 React 改 defaultValue 只改 attribute，不会改屏幕上显示的值。

影响复现路径：编辑「30 分钟初谈」→ 改标题为「40 分钟」→ 取消 → 点「编辑 60 分钟深度咨询」→ 弹窗里显示的是「40 分钟」。用户以为在改 B，实际表单里是 A 的内容，一保存就把 B 覆盖成 A。这是会写坏数据的交互缺陷。

建议最省事的一行：给表单加 key，让它在切换编辑对象时重建。

<form key={editing?.id ?? 'new'} id="event-type-form" action={handleSubmit}>

更彻底的做法是让 Dialog 在 !open 时返回 null（不渲染 children），或改成受控表单。

#7登录表单的 schema 被拿去校验登录凭证，密码错误和参数错误被混成一件事

位置 lib/auth.ts:30 · lib/schemas/auth.ts:7-10

现象authorize(credentials) 里用的是表单契约 loginSchema，它包含一条 callbackUrl 规则：「必须以 / 开头」。而 Auth.js 传给 authorize 的 credentials 就是整个 POST body（源码 @auth/core/.../callback/index.ts:326：const credentials = body ?? {}），里面一定带 callbackUrl。

实测已复现用绝对 URL 当 callbackUrl 直接打认证端点：登录失败，日志只留一行 CredentialsSignin，前端显示「邮箱或密码不对」。去掉 callbackUrl 就成功。

影响现在恰好没炸——因为 loginAction 总是传相对路径的 redirectTo。但只要有人把登录改成客户端 signIn('credentials', {email, password})（next-auth 最常见写法），Auth.js 会用 Referer 补一个绝对 URL 当 callbackUrl，登录当场全挂，而且报的是「密码不对」——排查方向完全是错的。这是埋着的雷，不是已经爆的雷。

建议拆成两个契约：凭证契约只认 email/password，callbackUrl 留在表单层单独校验。

// lib/schemas/auth.ts
export const credentialsSchema = z.object({
  email: z.email(),
  password: z.string().min(8),
})
export const loginFormSchema = credentialsSchema.extend({
  callbackUrl: z.string().startsWith('/', '回跳地址必须是站内路径').optional(),
})

// lib/auth.ts
const parsed = credentialsSchema.safeParse(credentials)

#16日历附件折行按「字符数」算，RFC 5545 要求「字节数」

位置 lib/utils/ics.ts:17-30

现象if (line.length <= 75) return line —— String.length 是 UTF-16 码元数，RFC 规定每行不超过 75 octets。一行 25 个汉字 = 25 个 length、75 个字节，刚好卡在边界；再多一个字就超了但代码不会折行。

影响中文标题或备注偏长时，生成的 .ics 不符合规范。Outlook 和部分安卓日历客户端对超长行会截断或直接拒收，表现为「附件加不进日历」。

建议按 Buffer.byteLength 折行，且不能从多字节字符中间切断：

function foldLine(line: string): string {
  const bytes = Buffer.from(line, 'utf8')
  if (bytes.length <= 75) return line
  const out: string[] = []
  let cur = ''
  for (const ch of line) {
    if (Buffer.byteLength(cur + ch, 'utf8') > 75) { out.push(cur); cur = ch }
    else cur += ch
  }
  out.push(cur)
  return out.join('\r\n ')
}
